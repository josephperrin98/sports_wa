# Decisions log

Short "why we did it this way" notes, in the order the decisions were made. Each says the decision, the alternative rejected, and the trade-off. Later notes can overturn earlier ones; the code and the [README](README.md) show where things ended up. "The brief" is my original project plan, which isn't published.

## Step 1: Setup

- **Python 3.12 in a standard `venv`, dependencies in `requirements.txt`.** macOS ships Python 3.9, which is old; Homebrew's 3.12 is already installed. We rejected `uv` (faster, has a lock file) because `venv` + `requirements.txt` is the standard library route that every host understands. Trade-off: no lock file, so versions get pinned by hand.
- **Secrets in a git-ignored `.env`, with a committed `.env.example` template.** The template shows which keys exist without containing any. Rejected: environment variables set by hand in the shell, which are easy to lose and hard to reproduce on a host.
- **Meta's WhatsApp Cloud API instead of Twilio (tried, then reversed, see the next note).** Twilio's free trial ends after 30 days, then needs a top-up of at least $20. Meta doesn't charge for replies to a message I sent ("All non-template messages are free", per its pricing page), and the bot only ever replies. Rejected: Twilio (costs money after the trial), unofficial WhatsApp Web libraries (break WhatsApp's terms, could get my personal number banned), Telegram (free and simpler, but I want WhatsApp). Trade-off: fiddlier setup. I need a permanent token from a system user, and a one-time webhook handshake. About 30 extra minutes.
- **Back to the Twilio sandbox, because Meta locked the account.** The first test send from Meta's free test number was accepted, then failed with error 131031, "Business Account locked". This is an automated integrity lock that others report on brand-new accounts too. The fixes are a business profile, possibly verification and a support ticket, and none of them has a known timeline. Rejected: waiting for Meta, which could take hours or days against a 4-hour budget. Trade-off: Twilio's trial ends after 30 days, enough for the build plus the one-week evaluation, so cost becomes a v2 question. Lesson: I spent about an hour before checking whether new accounts get locked. Next time, look up the known failure modes of a vendor's onboarding before committing the time budget to it. The WhatsApp-specific code goes in one module, so moving back to Meta later only changes that module.
- **The bot is a sports curator only, not a general assistant.** Section 4.7 of Meta's WhatsApp Business terms bans AI providers from the platform "directly or indirectly" when AI is the primary functionality on offer, so switching to a reseller like Twilio doesn't get around it. Meta judges what the WhatsApp number offers, not where the model runs. Enforced in the system prompt: politely decline anything that isn't about sports. Follow-ups that refine the same task are fine. Trade-off: I can't reuse the bot for anything else. Caveat: whether a narrow AI-powered curator counts as "primary" AI is Meta's call. A tight sports scope is the defensible position, not a guarantee.
- **SQLite log in v1, follow-up memory in v2.** Every question and reply goes into one SQLite table. SQLite is a database stored in a single file, built into Python, so no extra dependency. The week-long evaluation needs this log, so it isn't optional. Using the same table as conversation memory (so "what about Georgian TV?" understands the previous answer) waits for v2, unless we're ahead of schedule. Rejected: memory in v1, because it adds a feature before single question -> single reply is proven end to end. Trade-off: in v1 each message is answered on its own, without the earlier conversation.
- **No tunnel. Build locally with fake Twilio requests, then deploy to Google Cloud Run.** A tunnel (ngrok) wasn't available on my development machine. Rejected: running on my laptop at all for the evaluation (a week of real use needs a host that is on while my laptop sleeps). Google's free trial gives $300 for 90 days, which covers the build and the evaluation week. Trade-off: the first real WhatsApp test needs a deploy, so the feedback loop is slower. The trap to remember: Cloud Run cuts the CPU once a response is sent by default, which would freeze our background Claude call. Deploy with instance-based billing (`--no-cpu-throttling`).

## Step 2: Echo bot

- **Three small layers: `whatsapp.py` (Twilio formats), `service.py` (what to reply), and a FastAPI route that only connects them.** The service knows nothing about Twilio, so the Claude logic in step 3 can be tested without HTTP, and moving to Meta later only touches `whatsapp.py`. Rejected: one file with everything in the route. That's shorter today, but every later test would need a fake HTTP request.
- **Parse Twilio's form body with the standard library (`urllib.parse.parse_qs`) instead of FastAPI's form support.** FastAPI's form parsing needs an extra package (`python-multipart`), and step 4's signature check needs every field Twilio sent anyway. Trade-off: a few lines we wrote ourselves instead of a framework feature.
- **Echo replies inline with TwiML (Twilio's XML reply format).** It's the shortest way to prove the round trip, and it needs no Twilio credentials. Step 4 replaces it with a fast empty 200 plus a background reply via Twilio's REST API, because Claude is slower than Twilio's timeout.
- **Tests use the standard library's `unittest`, not `pytest`.** One dependency fewer. Trade-off: slightly wordier tests.
- **Code is written on the laptop, run in Google Cloud Shell.** Packages can't be installed from PyPI on my development machine. Cloud Shell is a free terminal on Google's machines, with Python 3.12, FastAPI and Google's deploy tool already installed, and it's where we deploy from anyway. Rejected: working around the machine's package setup. Trade-off: a slower loop, because every change has to be copied to Cloud Shell and the test output pasted back.
- **Versions pinned to what Cloud Shell has (`fastapi==0.141.1`, `uvicorn==0.52.1`, `httpx==0.28.1` for tests only).** The deployed app gets exactly the versions we tested. `httpx` lives in `requirements-dev.txt` because only the tests need it.
- **The route test skips itself when FastAPI isn't installed.** The laptop can then still run the other tests before and after every change, and Cloud Shell runs all of them.

## Step 3: Claude call, Serie A slice

- **Call the API over plain HTTPS with the standard library (`urllib`), not Anthropic's SDK.** One dependency fewer, the laptop can run every test without pip, and every line of the call is visible and explainable. Rejected: the official `anthropic` SDK, which is the normal choice and gives automatic retries on overload (429/529) and typed errors for free. Trade-off: no retries, so a busy API means "try again in a minute", and we wrote the pause handling ourselves. If overloads show up in the evaluation log, switching to the SDK means changing `app/claude.py` only.
- **Preferences in `preferences.toml`, read with the standard library's `tomllib`.** The brief sketched YAML, but reading YAML needs a package (PyYAML). JSON is built in but doesn't allow comments, and the comments explain my rules. Trade-off: needs Python 3.11+ (Cloud Shell has 3.12; the laptop needs the venv's Python, not macOS's 3.9).
- **Claude's built-in web search, never fixtures or channels from memory.** Rights change by season. Up to 5 searches per question, and the answer is the text after the last search (earlier text is Claude's working). If the server pauses a long search turn (`pause_turn`), we send the paused turn back and it carries on, at most 3 times.
- **Claude Opus 5.5 at medium effort, with automatic fallback if a safety check declines.** It's the strongest current model. Cost is logged per question (tokens, searches, estimated $) so the evaluation has real numbers. Rejected for now: a cheaper model, which is a one-line change once the log shows the cost. A sports question is unlikely to trip a safety check, but the fallback costs nothing unless it does.
- **The current time goes in the message, the rules in a fixed system prompt.** Claude needs the time to know what's "live". Keeping it out of the system prompt means the system prompt never changes, which is what prompt caching needs later. The time is sent in UTC and Claude converts it to my time zone. This avoids depending on time-zone data being installed on the server.
- **A failed call becomes a polite WhatsApp reply, not a server error.** Twilio would otherwise send nothing, and I wouldn't know whether the bot is broken or thinking. The real error goes to the logs.
- **The route runs the Claude call in a worker thread.** The call blocks for up to a minute, and blocking FastAPI's event loop would freeze every other request. Step 4 replaces this with a background task anyway.
- **First real answer (23 s) worked, but the format needed fixing.** Claude pasted search-result text into the reply and listed five channels for one match. Our code only reads the text Claude itself writes, so the fix was in the instructions: three fixed lines per event, no quoting sources, a real "why" reason or none. Rejected: cleaning the text up in code afterwards, which treats the symptom and breaks as soon as the wording changes.
- **Up to 3 channels per event, as a setting in `preferences.toml`.** Alternatives are useful when one stream doesn't work. It's a preference, so it lives in the config, where a test checks it, not in the prompt.
- **Times in New York time.** That's where I usually watch from. The time zone only changes how times are shown, not which country's broadcasters are searched (Serie A is still searched in Italian).
- **Twilio's ~15 s limit vs a 23 s answer.** Making Claude reliably faster (fewer searches, lower effort, a smaller model) trades away quality and still guarantees nothing. Step 4 instead answers Twilio within a second and sends the real reply later through Twilio's API.

## Step 4 (core): reply on the phone

- **Ack at once, answer in the background.** The webhook replies within a second with "On it…", which Twilio sends straight away. FastAPI's `BackgroundTasks` then runs Claude after the response has gone out, and the answer arrives as a second message via Twilio's Messages API. Rejected: making Claude faster to fit inside ~15 s, which costs quality and still guarantees nothing. Trade-off: two messages per question, and Cloud Run must keep the CPU on after responding (`--no-cpu-throttling`).
- **Check `X-Twilio-Signature` on every request, with standard-library `hmac`.** The URL is public, and each answer costs about $0.27. Without the check, anyone who found the URL could run up the bill or send messages as the bot. The recipe was checked in Twilio's own library code, and our test reproduces Twilio's published example signature exactly. Rejected: Twilio's Python library, a dependency for 10 lines. If the auth token is missing, every request is rejected ("fail closed").
- **The signed URL is rebuilt as `https://` + Host header + path.** Cloud Run hands the app plain HTTP behind its HTTPS front door, so the URL the app sees doesn't match what Twilio signed. Rejected: setting the URL as config, which can only be done after the first deploy and breaks if the URL changes.
- **Only my number gets an answer. Others get silence, not a polite no.** The signature proves the message came through Twilio, not that it came from me. Silence costs nothing. Rejected: relying only on the sandbox, which lets anyone in who knows the join code.
- **A `Dockerfile` instead of letting Google guess how to build.** Without one, Google's buildpacks choose the Python version and start command, and I couldn't confirm their defaults. The Dockerfile pins Python 3.12 (needed for `tomllib`) and the exact start command. `.gcloudignore` keeps `.env` out of the upload.
- **Secrets as Cloud Run environment variables, loaded from `.env` through a temporary file.** Typing them into the deploy command would save them in shell history. Rejected for now: Google Secret Manager, the better practice (encrypted, access-logged), at the cost of more setup. On a one-person project, the environment variables are only visible to me. Secret Manager is the upgrade if the project grows.
- **Deferred:** `MessageSid` dedupe. Twilio retries only when a webhook fails, and ours answers in under a second. Also the SQLite log: Cloud Run's disk is wiped whenever an instance restarts, so a SQLite file there would lose the evaluation data. Needs a decision before the evaluation week.

## Step 4 (deploy): what the first real run taught us

- **Deployed to Cloud Run. The build first failed with a 403 because Google's build robot (the Compute Engine default service account) couldn't read the upload.** New projects no longer grant it broad rights. Fix, from Google's docs: give it the Cloud Run Builder role (`roles/run.builder`). Rejected: the Editor role from older tutorials, which would let it change almost anything in the project.
- **The answer is collected with a second message, not sent.** The webhook and the Claude call both worked on the first real run (39 s, $0.285), but Twilio refused the second message with error 21654. Twilio's trial docs explain why: a trial account can't send free-text WhatsApp messages through the API, only Twilio's own templates, and creating our own template is paid-only too. A message straight back in the webhook reply still works. So the first message starts the search ("On it, send me any message in about 45 seconds"), and the next message collects the answer as its instant reply. Rejected: upgrading Twilio (my choice not to pay; it would make the original two-message design work unchanged); answering within Twilio's ~15 s (doesn't fit with live search, and a slow answer would be silently lost).
- **The waiting answer lives in memory, in one slot, behind a lock.** I'm the only number answered and Cloud Run runs a single instance (`--max-instances 1`), so the background search and my next message reach the same process. Checking and claiming the slot happen under one lock, so a search finishing in between can't be lost. A message during the search gets "Still checking" and never starts a second, paid search. An answer older than 10 minutes is dropped (it's about what's live), and a search stuck for over 5 minutes is given up on. A crash during the search leaves an apology in the slot rather than "Still checking" forever. Rejected: a database (Firestore), which is more setup for one slot; losing the answer on a restart only means asking again. Trade-off: the collecting message's own text is ignored; it only collects.
- **Removed the REST sender (`send_message`) and the two settings only it used.** Unused code is code I'd have to defend. It's in git history (commit `3374142`) if I ever upgrade Twilio.

## Step 4 (tiers): every tier, team boosts, tennis and the wildcard

- **The whole of the brief's config lives in `preferences.toml`, not in the prompt.** Tiers 1-4 as a list of competitions; tier 5 is "anything not listed", computed as the last tier + 1, so adding a tier needs no code change. Team boosts are their own list, ranked above every tier. A competition names a language only where it differs from the league's own (cycling and Top 14 in French); the language rules cover the rest. The France football team is a team boost only, since boosts already outrank tier 1.
- **Search in a fixed order to keep the number of searches down: broad schedule searches first, then channels only for the shortlist, then the wildcard.** This is the brief's "search only for the shortlisted 3-5 events", done inside one Claude call. Searches go up from 5 to 10, so I expect about twice the cost and time (roughly $0.50-0.60 and a minute; the cost log will give the real number). Rejected: one search per league, which can't fit five tiers. Rejected for now: a separate Claude call to shortlist first, which costs more code and a second round trip. The per-request timeout went from 120 s to 180 s to match.
- **The wildcard needs a `Source:` link.** The brief's biggest risk was an invented obscure event. A link lets me check it during the evaluation week. Not built yet: "no repeat within 14 days", which needs a memory of past replies (the evaluation log). It isn't in the prompt, because telling Claude to follow a rule it can't check would hide the gap.
- **Two fixes from the first phone answer.** Claude gave 2 events when the minimum is 3, so the prompt now says "always reach 3: add the next upcoming ones". And times now carry a label from the config (`timezone_label = "ET"`), so "12:30 PM" is never ambiguous when I travel. Rejected: computing the label from time-zone data, which slim server images may not include.
- **Champions League and Europa League: search in the home team's language (the brief's open item, decided 2026-10-18).** I kept the brief's rule rather than "the team I'd naturally follow". Rule 2 now says outright that international cups have no language of their own; otherwise Claude could take English (UEFA's working language) and never reach the home-team rule. Lyon, Nice and France still get French even away, because team boosts set their language in rule 1.

## Step 4 (tuning): first all-tiers answer from the phone

- **Today only, and the minimum comes from lower tiers, never other days.** The first answer had a Thursday game and a Saturday game. That was caused by my own fix one round earlier ("always reach 3: add the next upcoming ones"). Now an event must be live or start before midnight New York time, and the 3-event minimum is reached by going down the tiers to tier 5 ("anything else"), which almost always has something on today. If there really are fewer, the reply is shorter. This replaces "starting soon = 3 hours", a default that was never confirmed. I want the whole day.
- **Men's teams and competitions only, as a setting (`mens_only`).** Claude listed OL Lyonnes (Lyon's women's team) as a Lyon team boost. The rule names that exact case as its example.
- **No source link in the reply.** I don't want links in the message, so I reversed last round's `Source:` line. Trade-off: a made-up wildcard is harder to catch at a glance. The prompt still requires an event found in a search. If the evaluation shows invented wildcards, the place to put the source is the log, not the message.
- **The wildcard must be little-known.** Claude picked the MLB World Series, the opposite of the brief's kok boru example. Now: a sport most people in France or the US have never watched, never a major league or a sport from my tiers.
- **The search budget is split up front (about 3 for the schedule, about 1 per event for channels, 1-2 for the wildcard), and Claude may not narrate its searches.** The first answer ran out of searches, partly by spending them on a game that had already ended, then said so in the reply, and found no channel for either French game. The prompt reads the limit from `claude.MAX_SEARCHES`, so the two can't drift apart. Not raised above 10 yet: I'll judge from the next answer and its cost line.
- **The app picks a random wildcard region for each reply.** The tuned answer's wildcard was sepak takraw, one of the two examples in the rule: examples in a prompt become defaults. Rewording alone wouldn't last, because Claude never sees its past replies, so "vary it" can't work. The app now picks one of 14 regions (standard library `random`) and puts it in the message, next to the time, so the system prompt stays fixed. The examples stay, marked as showing the kind of sport only. This is variety, not a guarantee: the "no repeat within 14 days" rule still needs the evaluation log.
- **Cost accepted for the test: $0.29 to $0.75 per question.** Same 10 searches, from 58k to 143k input tokens, depending on how long the pages are. My call: low use, a demo for GitHub, so no cost work now.
- **The wildcard must be watchable right now, with a fallback order instead of "channel not found".** The next answer's wildcard (Basque pelota) came with no way to watch it: the rule said what to deliver but not what to do when the channel search fails. Now: live or a replay available now (never later); if no channel, another event in the same region, then anywhere. I wanted it mandatory, but kept one last resort: leave the wildcard out rather than invent one, because a rule that forces an answer is how the brief's "wildcard hallucination" risk happens. The heading says "one per reply", not "exactly one", so the rules don't contradict each other.

## Step 5 (evaluation): logging every answer

- **One JSON line per answer in Cloud Logging, not SQLite.** The brief planned a SQLite file, but Cloud Run wipes the container's disk on every restart, so the evaluation week would be lost. Cloud Run already sends the app's log lines to Cloud Logging, which keeps them for 30 days, enough for a one-week evaluation. So the log is one line through the standard `logging` module: the time, my question, the wildcard region and the full reply. Rejected: Firestore or a file in Cloud Storage, which last longer but each add a dependency and a permission to set up. Trade-off: after 30 days the lines are gone unless I export them, which the evaluation does anyway.
- **The line is written in the service, right after Claude answers, failures included.** An apology is an answer I got, so it counts in the evaluation. The cost is not in this line: it's already in the `claude ...` line before it, and putting it here would mean changing what `claude.ask` returns.
- **The export is a module (`app/evaluation.py`) that reads gcloud's JSON from a pipe and writes a CSV.** gcloud fetches the lines, and Python only turns them into a sheet, with the standard `csv` and `json` modules. Rejected: calling gcloud from Python (`subprocess`), which hides the command I'd want to adjust, and a Google Sheets API integration, which means a dependency plus access to my Drive. What can be counted from the reply's fixed format (events listed, wildcard present) is filled in. Whether a channel was right needs me to check it, so those columns stay empty. Rejected: letting Claude grade the answers, because it would search the same pages and miss the same mistakes. A malformed line stops the export instead of being skipped, so no answer silently drops out of the count.
